# Time-based work runs as periodic DB sweeps; messages go through a transactional outbox; BullMQ only executes

Rule values that drive timers (reserve hours, reminder offsets, review delay, wait windows) are admin settings that can change at any time, so we don't schedule a delayed job per order or right. The single worker runs **sweeps** every minute that select what is due straight from the DB (`reserve_until < now()`, `expires_at - 7 days < now()`, …). Each send stamps a marker (`reminder_7d_sent_at`, `review_requested_at`, …) in the same transaction that queues it, so a sweep that runs twice sends nothing twice. State changes and their customer messages commit together through a **transactional outbox**, so a crash after commit never loses a notification.

**BullMQ** on Redis only executes work: receipt AI checks, Telegram sends, broadcasts, with retries, backoff and the receipt or outbox id as `jobId`. Daily jobs (birthday coupons at 10:00) are repeatable jobs with `tz: 'Asia/Tashkent'`. Telegram sends go through grammY `auto-retry` plus a throttler, with broadcasts at ≤ 25 msg/s. A 403 marks the customer `bot_blocked`, which reports show as «не доставлено».
