# The orders-group card is a state row, rendered from the order when the outbox delivers it

Ticket #37 needs one message per paid order in the orders group, edited on every change whoever made it (the group's buttons, the admin panel, a sweep). Two things decide the design: the card's Telegram message id is only known after the first send, and the outbox delivers rows in parallel (five at a time, with retries), so edits rendered when the change happened could land in the wrong order and leave an old card on screen.

So the card is a row, `order_cards` (one per order: the group and topic, the message id once posted, the receipt to reply with, the keyboard state, a version and a hash of what Telegram shows). `transition()` gets **listeners that run after every move inside its transaction** (`OrderStatusService.afterMove`): the card's listener opens the row on `confirm_payment` and bumps the version on any other move. Each bump queues an outbox row of a new **kind**, `order_card` (`outbox.kind`, `outbox.ref` = the order id; message rows stay `message`). The outbox claims and retries it like a message and hands it to the handler registered for its kind (`OutboxService.handle`). The handler takes the card's lease (`syncing_at`, expiring after `outbox.requeueAfterSeconds` like the outbox's own claim), renders the card **from the order as it is now**, posts it or edits it only when the hash differs, sends the receipt once, and releases the lease only if no newer version arrived meanwhile (otherwise it goes round again). A delivery that finds the lease taken is retried by the queue. So the newest state always ends on screen, a crash loses nothing, unchanged cards cost no API call, and rate limits stay with the sender (`apiThrottler`, `auto-retry`). The sender edge gains `edit()`, which treats "message is not modified" as success and tells a gone message apart (`MessageGoneError`), so a deleted card is posted again.

## Considered Options

- **Render the text when the change happens and queue an edit row.** Rejected: parallel delivery can apply edits out of order, and an edit queued before the first post has no message id to edit.
- **A dedicated BullMQ queue and sweep for cards.** Not chosen: the outbox already gives the after-commit dispatch, the claim, retries and the minute tick; a task kind reuses all of it.
- **Hold a database lock during the Telegram call.** Rejected: a 429 retry can hold it for a minute; the lease column gives the same exclusion without an open transaction.
