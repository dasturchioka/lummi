# Docker Compose on the VPS, images from GitHub Actions, migrations before start

Production (customer VPS) and staging (Sardor's VPS) run the same Compose file with different `.env`: `caddy` (automatic TLS, reverse proxy, serves the Mini App build and `/media/public`), `api` and `worker` (one image, two entrypoints), `admin` (Next.js standalone), `userbot`, and `postgres` and `redis` with no published ports. Hosts: `<domain>` Mini App, `api.<domain>` API + bot webhook, `admin.<domain>`, `media.<domain>`.

GitHub Actions runs lint, typecheck, tests and the 27/30 search gate, then builds images to GHCR. Deploy is an SSH step: `docker compose pull`, migrations in a one-off `api` container, then `up -d`. `main` deploys to staging; production deploys only from `v*` tags. A few seconds of restart are acceptable, because Telegram redelivers webhook updates. Hosts run Ubuntu 24.04 LTS with key-only SSH, `ufw` (22/80/443), `fail2ban` and `unattended-upgrades`. Apps log JSON with pino under Docker log rotation; errors and staff actions are also persisted in the DB (TZ §9).

## Amendment 2026-11-11: stage 1 deploys from `stage-1`; build-time values; staging behind host nginx

- **Deploy branch.** During stage 1 all work lands on `stage-1`, and `main` only receives it when the stage-1 PR merges. The staging deploy job (`.github/workflows/deploy.yml`) therefore runs on pushes to `stage-1` and `main` and on `workflow_dispatch`, after the CI `check` job passes; never on other branches or PRs. Production still deploys only from `v*` tags.
- **Staging host.** Sardor's VPS is shared; its nginx owns 80/443 and proxies the four hosts to Caddy on `127.0.0.1:4180` (`CADDY_SCHEME=http://`). Production keeps Caddy on 80/443 with automatic TLS. Secrets live only in `/opt/lummi-staging/.env` on the VPS; CI holds the SSH secrets and uses `GITHUB_TOKEN` for GHCR (also for the VPS pull). Run guide: `docs/run-guide.md`.
- **Build-time values.** The Mini App reaches the API through same-origin `/api` and photos through `/api/media/public`, so one image fits any domain. The only baked value is `VITE_BOT_LINK` (share links), a build arg from the GitHub variable `STAGING_BOT_LINK` (production: its own). The admin reads `API_URL` and `BOT_USERNAME` at run time.
- **Seed.** The deploy runs migrations, then `seed-staging` (catalog only while the catalog is empty, missing BTS points), then `up -d`; the API sets the webhook and menu button at boot (`BotService.start`), so there is no second copy of that code. `.deploy.env` is written only after a successful deploy (rollback: run guide). The owner is added once by hand with `seed:owner`.
- **Files volume.** Caddy mounts only the `public/` subfolder of the files volume, read-only.
