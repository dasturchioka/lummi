# The userbot keeps its session sealed at rest and in memory at run time, reads one env-pinned chat, and beats only when caught up

Ticket #19 builds the userbot of ADR 0014 as `apps/userbot` (mtcute, pinned to 0.32.7 with its family through root `overrides`; an upgrade is its own change, since mtcute holds a login). It runs in its own container and only calls the API's internal endpoints (ADR 0031): it never touches the DB.

- **Session.** The login CLI (`src/cli/login.ts`, run by hand in the container) takes phone, code and 2FA password, and writes the mtcute session string sealed with AES-256-GCM under `USERBOT_SESSION_KEY` (32 random bytes in `.env`) to one owner-only file on the `userbot-data` volume. At run time mtcute uses **in-memory storage**: the sealed file is the only copy at rest, and mtcute never writes an auth key to disk. A fresh in-memory session knows no chat's access hash, so the first call that needs a chat finds it in the account's dialogs (at most 500, once per start). The session, the key and message texts never reach a log or an error; the device shows as «LUMMI userbot» under Settings > Devices.
- **What it reads.** The listened chat is `USERBOT_LISTEN_CHAT_ID`, a server value, **not an admin setting**: anyone who could change it could pipe any private chat of the customer's personal account into our DB. It handles only messages the other side sent there (not the account's own, not service messages). The forward target comes from the API (`GET /internal/userbot/forward-target` = `bot.groupChatId` + `bot.topics.payments`, the «Поступления» topic), read on every forward, so a group that becomes a supergroup is followed.
- **Order of work.** One task at a time: post (retried with backoff until 2xx, nothing after it posted meanwhile), then forward a ➕. The post comes first because the credit, not the group message, is what matching needs; a forward Telegram refuses, or a flood wait over 120 s, is logged and skipped. A crash between the two loses that one forward, never the credit.
- **Catch-up.** On start, after the API's last stored id; after every reconnect (and after mtcute's own `updating`), after the last id it handled, by reading the history before anything that arrived meanwhile. With **nothing stored yet**, it starts after the newest message in the chat: the account's past card history is not imported. So a message that arrives while it is down before anything was ever stored is missed; the run guide's first step after login is a test ➕, which sets the starting point.
- **Heartbeat** (#36): every minute, only when connected, caught up and with nothing waiting to post, and only after a `getMe` call succeeds, because a revoked session can leave the link itself up.
- **Stopping.** A dead session (`AUTH_KEY_UNREGISTERED`, `SESSION_REVOKED`, …), a missing or unopenable session file, or a listened chat the account cannot see **parks** it: one error line, no heartbeats, no further Telegram calls, and the process stays up so Compose does not restart it into a loop. The stale heartbeat is the alert (#36, ADR 0025). Anything else unexpected exits, Compose restarts it, and catch-up covers the gap.

## Considered Options

- **mtcute's SQLite storage on the volume.** Rejected: it holds the auth key in clear, which defeats sealing the session.
- **The listened chat as an admin setting** (ADR 0023 says "a setting"). Rejected for the reason above; it is per-environment server config.
- **Forward first, then post.** Rejected: a slow or flood-limited forward would delay the credit, and a crash between them would forward twice.
- **Backfill some hours of history when nothing is stored.** Rejected: it would import the customer's own card history and alert the owner for every non-operation message in it.
