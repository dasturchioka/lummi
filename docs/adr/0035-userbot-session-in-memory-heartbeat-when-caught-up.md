# The userbot keeps its session sealed at rest and in memory at run time, reads one env-pinned chat, and beats only when caught up

Ticket #19 builds the userbot of ADR 0014 as `apps/userbot` (mtcute 0.32.7; every `@mtcute/*` package it pulls in is pinned in root `overrides`; an upgrade is its own change, since mtcute holds a login). It runs in its own container on a Compose network it shares only with the API (`userbot`, 172.28.1.0/24, the one subnet in `INTERNAL_ALLOWED_CIDRS`), read-only, without capabilities or privilege gain, and only calls the API's internal endpoints (ADR 0031): it never touches the DB.

- **Session.** The login CLI (`src/cli/login.ts`, run by hand in the container) takes phone, code and 2FA password, and writes the mtcute session string sealed with AES-256-GCM under `USERBOT_SESSION_KEY` (32 random bytes in `.env`) to one owner-only file on the `userbot-data` volume. It refuses an account without a two-step password, and ends the new session whenever it does not save it. At run time mtcute uses **in-memory storage**: the sealed file is the only copy at rest, and mtcute never writes an auth key to disk. A fresh in-memory session knows no chat's access hash, so the first call that needs a chat finds it in the account's dialogs (at most 500). A chat not found there is looked for again at most every 10 minutes, so a group the account is not in costs one scan per period, not one per ➕. The session, the key and message texts never reach a log or an error; the device shows as «LUMMI userbot» under Settings > Devices.
- **What it reads.** The listened chat is `USERBOT_LISTEN_CHAT_ID`, a server value, **not an admin setting**: anyone who could change it could pipe any private chat of the customer's personal account into our DB. At start it must be a bot, and with `USERBOT_REQUIRE_VERIFIED=true` (production; not tied to `NODE_ENV`, which staging shares) a bot with Telegram's verified tick; otherwise it parks. Every other chat's messages are dropped on their raw chat id, before their sender or text is read. It handles only messages the bot sent (not the account's own, not service messages). The forward target comes from the API (`GET /internal/userbot/forward-target` = `bot.groupChatId` + `bot.topics.payments`, the «Поступления» topic), read on every forward, so a group that becomes a supergroup is followed.
- **Order of work.** Posts, one at a time (retried with backoff until 2xx, nothing after it posted meanwhile), then a ➕ the API had not seen before (`duplicate: false`) goes to the forwards, a queue of its own. The post comes first because the credit, not the group message, is what matching needs; a forward never holds back a post or the heartbeat. A forward Telegram refuses, or a flood wait that is not short, is logged and skipped. A crash between the two loses that one forward, never the credit; a repeat never forwards twice.
- **Catch-up.** On start, after the API's last stored id; after every reconnect (and after mtcute's own `updating`), after the last id it handled, by reading the history before anything that arrived meanwhile. With **nothing stored yet**, it starts after the newest message in the chat: the account's past card history is not imported. So a message that arrives while it is down before anything was ever stored is missed; the run guide's first step after login is a test ➕, which sets the starting point.
- **Heartbeat** (#36): on its own one-minute timer, only when connected, caught up and with no post waiting, and only after a `getMe` call succeeds, because a revoked session can leave the link itself up. No single flood-wait sleep is longer than half the smallest allowed `payments.heartbeatStaleSeconds` (59 s), so a wait of ours never looks like a dead feed; mtcute answers an early retry itself.
- **Stopping.** A dead session (any 401, and `AUTH_KEY_DUPLICATED`, at start or later), a missing or unopenable session file, or a listened chat that is wrong or out of reach **parks** it: one error line, no heartbeats, no further Telegram calls, and the process stays up (closing the dead client may fail; that is ignored) so Compose does not restart it into a loop. The stale heartbeat is the alert (#36, ADR 0025). Anything else unexpected exits, Compose restarts it, and catch-up covers the gap. It has no Docker healthcheck, since a parked userbot would fail every `up --wait` deploy.

## Considered Options

- **mtcute's SQLite storage on the volume.** Rejected: it holds the auth key in clear, which defeats sealing the session.
- **The listened chat as an admin setting** (ADR 0023 says "a setting"). Rejected for the reason above; it is per-environment server config.
- **Forward first, then post.** Rejected: a slow or flood-limited forward would delay the credit, and a crash between them would forward twice.
- **Backfill some hours of history when nothing is stored.** Rejected: it would import the customer's own card history and alert the owner for every non-operation message in it.
