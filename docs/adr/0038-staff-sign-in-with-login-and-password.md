# Staff sign in with a login and password; Telegram is bound through the bot

Amended in part by #64 (2026-11-18): owners can be added and promoted in the panel (see "What stays").

Amends ADR 0017. Decided by Sardor on 2026-11-14 (ticket #50): the shop has an owner and several managers, and the Telegram Login Widget alone is a hard way in for them (it needs the bot's domain set with BotFather, a Telegram session in the browser, and an owner who knows each manager's numeric id). **Login and password become the main way into the admin panel; «Войти через Telegram» stays as the second button.** The owner creates the managers' accounts and hands them their passwords.

What stays from ADR 0017: one `staff` table gates the panel and the orders-group buttons; the session is the same httpOnly, revocable cookie; group buttons know a presser only by Telegram id; the first owner is created by the server CLI, and from #64 an owner can add other owners and change roles in the panel (never their own role, never leaving the shop without an active owner); every account action is audited with its actor.

## Decisions

- **Accounts.** A staff record gains `login` (stored lower case, so unique case-insensitively; 3–32 of `a-z 0-9 . _ -`), `password_hash` and `must_change_password`. `telegram_id` becomes optional (still unique when set). A record always keeps a login or a Telegram id (check constraint). Records from before #50 keep their Telegram id and no login; they sign in with the widget as before, and their sessions survive the migration (`0031_staff_passwords` adds columns, tables and checks, and only relaxes `telegram_id` to nullable).
- **Hashing: argon2id from `node:crypto`.** Node 24.7+ ships `crypto.argon2` (OpenSSL 3.2+), so there is no dependency and nothing to compile in the `node:24-slim` image (the `argon2` npm package needs prebuilt binaries or build tools; `@node-rs/argon2` ships a native addon per platform). Cost is OWASP's argon2id baseline (19 MiB, 2 passes, 1 lane, 16-byte salt, 32-byte tag), stored as a PHC string `$argon2id$v=19$m=…,t=…,p=…$salt$hash`, so it can rise later without breaking old hashes. A unit test checks the reference implementation's test vector. The cost is a cryptographic parameter, not a shop rule, so it is not a setting. A sign-in for a login that does not exist, or a record without a password, still runs one derivation, so the answer takes as long and reads the same: «Неверный логин или пароль» (401 `invalid_credentials`).
- **Temporary passwords.** The panel generates them in the browser (`crypto.getRandomValues`, 16 characters from 56 letters and digits without look-alikes, about 93 bits; longer if the minimum asks), and the owner may type one instead. The API never returns a password: the panel shows the one it sent, once, with a copy button and «Показывается один раз». A temporary password sets `must_change_password`; until it is changed, the staff guard answers 403 `password_change_required` to everything but who-am-I, the password policy, the change itself and sign-out, and the panel shows only «Смените пароль».
- **Sessions.** «Сбросить пароль» (owner, managers only) and the CLI's new owner password end every session of that member in the same transaction. A member's own change ends their other sessions and keeps the current one. Deactivation still ends every session (ADR 0017).
- **Locks.** Wrong passwords count per login and per client address in `login_throttles`: `auth.passwordAttemptsPerLogin` (5) or `auth.passwordAttemptsPerIp` (20, over any logins) failures within `auth.passwordAttemptWindowSeconds` (900) lock that login or address for `auth.passwordLockSeconds` (900). While locked, no password is checked at all, and the answer is 429 with `retryAt`; the panel says until when. A right password restarts that login's count (an address keeps its count). A login lock of an existing member is audited (`staff.locked`), an address lock as `auth.address_locked`. Wrong current passwords in «Сменить пароль» count toward the login's lock too. The minimum length is `auth.passwordMinLength` (8). The client address is `X-Real-IP`. Every Caddy route to the API (the Mini App's `/api/*`, `api.<DOMAIN>`, the admin's `/api/*`) goes through one snippet that sets it from `{client_ip}`, overwriting whatever a client sent; `{client_ip}` is resolved through `trusted_proxies` in strict mode (read from the right of `X-Forwarded-For`, skipping only trusted hops), so a value a client puts in front is never taken. The API's port is published to nobody. Admin routes answer only through `admin.<DOMAIN>`: the Mini App host and `api.<DOMAIN>` answer 404 to `/admin/*`. Each attempt is counted before its password is checked, under a row lock, so a burst of parallel guesses gets no more than the limit and the rest are refused without running argon2; a right password takes its attempt back.
- **«Привязать Telegram».** A member asks the panel for a one-time link `t.me/<bot>?start=staff_<token>`: 24 random bytes as 32 base64url characters, only the SHA-256 stored, valid for `auth.telegramLinkTtlSeconds` (600), a newer link replacing an unused older one. The `staff_` prefix keeps it apart from the Mini App's `startapp` values (`p_…`, `l_…`, the fixed targets). The bot's `/start staff_<token>` binds that Telegram account to the member once, in the update's transaction, and answers in that Telegram's language; it creates no customer and sends no greeting. A Telegram account bound to another member is refused without using the link up; a switched-off member's link binds nothing. The profile page polls who-am-I and confirms once the bot has bound it. A member who already has Telegram bound cannot make a link (409 `already_linked`); the owner unlinks a manager's Telegram, unless it is that manager's only way in (409 `telegram_only`).
- **Group buttons** are unchanged: the presser is found by Telegram id and must be active. A Telegram account bound to nobody now reads «Нет доступа. Если вы сотрудник, привяжите Telegram в админке: Профиль → «Привязать Telegram».» (there is no way to tell a manager who has not linked yet from a stranger); a switched-off member still reads «Нет доступа».
- **CLI.** `seed:owner` takes `--login` (with or without `--telegram-id`; it adds whichever the record lacks) and never touches a password. `set-owner-password --login <login>` generates a temporary password, prints it once in the terminal (the only place a password is shown outside the panel), stores its hash, forces a change at the next sign-in and ends the owner's sessions: it is both the first set-up and the lost-password recovery.
- `ADMIN_DEV_LOGIN` and its `POST /admin/auth/dev {telegramId}` are unchanged (dev and tests only).

## Considered Options

- **Server-generated temporary passwords returned in the response.** Rejected: then a password travels in a response body and in whatever logs or traces see it. Generating in the browser keeps the rule simple: no response ever carries a password, and a test asserts it over every body.
- **Locks in Redis with TTL keys.** Rejected: the lock must follow the test clock (Seam 1 fakes the clock, not Redis), and a table keeps the counts beside the audit entries; the rows are pruned on each failure.
- **Linking Telegram by typing an id in the panel (as before).** Rejected for staff self-service: anyone could claim any id; the bot link proves the account.
- **The `argon2` npm package.** Not chosen: a native addon for no gain over Node's own implementation.
