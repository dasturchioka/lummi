# Backups run from a host timer; errors and the worker heartbeat live in our own database

**Backups** (ADR 0020, 0025) are a systemd timer on the host (`deploy/backup/`), not a Compose service. The restore test needs a throwaway Postgres container and the second copy needs the `files` volume and ssh; from inside a container that means mounting the Docker socket, which is root on the host. The host needs only `age`, `rsync` and Docker, and `OnCalendar=*-*-* 03:00:00 Asia/Tashkent` fixes the time whatever the host's timezone. `pg_dump -Fc` streams into `age` (no plaintext dump on disk); the owner holds the private key offline, the server only the public one. The second copy is env-configured (`BACKUP_RSYNC_TARGET`) because the customer has not named it yet; unset means a warning and a skipped step, and `--dry-run` shows what would be sent.

**Errors** go to the `error_events` table, no foreign tracker. A fingerprint is the SHA-256 of the error class (a failed query by its SQLSTATE), the route pattern and the top three application stack frames without line numbers. The message, query string and ids are never stored, because messages and parameters carry personal data (the same rule as `describeError`). The first insert of a fingerprint queues one Telegram message to the developer (`ops.developerChatId`) through the outbox in the same transaction; repeats raise `count`.

**Worker heartbeat.** The worker stamps `worker_heartbeat` at the start of every tick; the API checks it every minute and alerts after `ops.workerSilentSeconds` (180), once per outage plus once on recovery, with the state (`outage_alerted_at`) in the row. An alert is first claimed with a short transaction, then sent after the commit (no Telegram call under a row lock), and the claim is undone if every send failed. Recovery requires a beat newer than the alert. The alert goes straight to Telegram, not through the outbox, since the outbox is delivered by the worker that is down. Silence is measured from the later of the last beat and the API's own start, so a deploy gap does not alert.

**The second copy cannot erase itself.** The VPS only adds dumps and secrets there (dated names, no `--delete`, no overwrite); the target rotates by date with its own script, ideally behind `rrsync -no-del`. Receipts are mirrored **encrypted per file** with `age` (`private-enc/`), the only tree the VPS may delete in, capped per run. The owner's private key never lives on the VPS; the restore test runs where the key is.

**Every failure and skip alerts.** systemd `OnFailure=` for any failed run (incl. timeout and kill); the script reports finished runs to `POST /internal/backup/report`; the API alerts when no report arrives for `ops.backupStaleSeconds` (26 h) and, once a day, for skipped steps.
